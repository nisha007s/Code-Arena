# Code Arena on Supabase (₹0 deployment)

**Live site:** https://code-arena-orpin.vercel.app (Vercel project `code-arena`, Hobby plan) · **Backend:** Supabase project `kyabmrwffikjivbbqvln` (Free plan).

The public deployment runs entirely on **Supabase Free** (backend) and **Vercel Hobby** (static frontend).
The original Express + Socket.IO + SQLite + Docker backend is unchanged in `server/` and still runs
locally (`npm start`); the branch `backup/docker-backend` preserves it exactly as it was before the migration.

## Architecture

```
Browser (existing HTML/CSS/vanilla JS, served by Vercel)
 ├─ supabase-js (vendored: public/vendor/supabase.js, no CDN)
 │   ├─ Auth: anonymous sign-in = guest session (JWT in localStorage)
 │   ├─ Postgres RPCs (SECURITY DEFINER, row-level security everywhere): session, problems,
 │   │   rooms, ready/start/rematch, snapshots, history, attempts
 │   └─ Realtime: UPDATE notifications on the rooms row (RLS-filtered) → refetch own snapshot
 └─ POST /functions/v1/judge  (code and input base64-encoded)
       judge ── lease a lane (Postgres) ──► run-js-{1..3} | run-pya-{1..3} | run-pyb-{1..3}
                                             QuickJS-WASM      CPython 3.15 WASI (problems 1–6 / 7–12)
Postgres: pg_cron every 15 s → deadlines, settle window, dead jobs, disconnects, lobby grace
```

| Original | Supabase replacement |
|---|---|
| Cookie guest session | Anonymous sign-in + `profiles` |
| SQLite tables | Postgres (`supabase/migrations/`) with RLS on every table |
| Express API | RPCs (`ca_*`) + `judge` Edge Function; `public/js/api.js` keeps the same `/api/...` JSON shapes |
| Socket.IO | `public/js/realtime.js`: Realtime notifications + 10 s heartbeat (same events for `arena.js`) |
| In-process timers | Deadlines stored in `rounds`; checked on every snapshot/heartbeat and by pg_cron |
| Docker judge (5 languages) | WebAssembly judge (Python, JavaScript) |
| Server-side recommender | Same algorithm in the browser (`public/js/recommender.js`) on the guest's own verdicts |

## The WebAssembly judge

* **Python**: CPython 3.15.2 WASI build (pinned SHA-256), debug sections stripped, memory capped at
  128 MiB, every loop metered so the module calls back into the runner about every 20,000 iterations;
  the runner checks the clock and stops the program inside the sandbox at the time limit (C-level loops
  such as huge integer powers or regex backtracking included). Python only sees stdin, stdout, stderr and a
  read-only in-memory standard library: no network, files, environment or JavaScript bridge.
* **JavaScript**: QuickJS compiled to WebAssembly with an interrupt-based time limit and a 64 MB memory
  limit. Programs see only `require('fs').readFileSync(0)`, `console.log` and `process.stdout.write`.
* **Lanes**: Supabase runs several requests in one worker and kills the whole worker when its shared CPU
  budget is exceeded. Each runner function therefore has at most one request in flight (a Postgres lease
  in `runner_lanes`), so one student's code can never share a worker with another's. One lane of each
  kind is kept for battle submissions.
* **Cold workers** answer their first request with `{ warming: true }` after an unmeasured warm-up run
  (lazy WebAssembly compilation); the judge then re-sends the test. Student code never runs cold.
* **Classification** (no retry for anything student code can cause): runner reply with a verdict → final;
  `546 WORKER_RESOURCE_LIMIT` → TLE "time or memory limit exceeded" (possible only for the request itself,
  thanks to lanes); anything else → one retry, then **Judge Unavailable**, which voids a battle round if it
  could have changed the result. Accepted is reported only when every test's output matched.
* **Hidden tests** live only inside the runner bundles (git-ignored, built by `npm run supabase:build`).
  Expected outputs never enter the sandbox; hidden tests return only a verdict.
* **Firewall**: Supabase's edge firewall blocks HTTP bodies containing text such as `/etc/passwd`, so
  code, custom input and results always travel base64-encoded and are decoded inside Postgres.

### Resized tests and limits (fairness)

QuickJS has no JIT, so the largest hidden tests of 7 problems were reduced (constraints in the problem
statements match): Target Pair n ≤ 40000, First Occurrence n ≤ 100000, Longest Streak n ≤ 150000,
Maximum Segment Sum n ≤ 80000, Merge Maintenance Slots n ≤ 25000, Next Warmer Day n ≤ 80000,
Cheapest Route n ≤ 20000 / m ≤ 40000. Original fixtures and `fixtures.lock.json` are untouched; the
resized copies are generated by `scripts/supabase/make-fixture-generator.cjs`.

Time limits per problem and language are 3 × the slowest reference run on Supabase, between 0.5 s and
1.2 s (`supabase/judge-limits.json`, evidence in `supabase/judge-calibration.json`). Fairness check:
slow-but-correct solutions (`scripts/supabase/slow-solutions/`) get exactly the verdicts they got on the
original tests with the original Docker limits (`baseline-original.json`): TLE for 01, 05, 07, 10, 11 and
Accepted for 03, 04 (whose input reading is already O(n)), in both languages.

## Free-plan safety

* No paid resource is used; Supabase Free and Vercel Hobby cannot bill.
* The judge refuses new code once **425,000** judge-related calls are recorded in a month (free quota
  500,000). `npm run supabase:usage` prints usage; the Supabase dashboard is authoritative.
* Limits per guest: one job judging at a time, 12 runs/submissions per minute, 5 rooms per minute,
  64 KB code and input. Anonymous sign-ins: 30 per hour per IP (Supabase default).
* Free projects pause after 7 days without activity; restore from the dashboard (data is kept).

## Deploy / redeploy

Prerequisites: `npx supabase login` and `npx vercel login` (browser sign-in; never paste tokens).

```bash
npx supabase@2.58.5 link --project-ref kyabmrwffikjivbbqvln
npx supabase@2.58.5 db push --linked                   # migrations
npm run supabase:build                                  # Python runtime, resized fixtures, 9 lanes
for f in judge run-js-1 run-js-2 run-js-3 run-pya-1 run-pya-2 run-pya-3 run-pyb-1 run-pyb-2 run-pyb-3; do
  npx supabase@2.58.5 functions deploy $f --project-ref kyabmrwffikjivbbqvln --use-api
done
npx vercel@latest deploy --prod                         # static frontend (public/ only, see .vercelignore); the CLI must be 47.2.2 or newer
```

Function secrets (`RUNNER_KEY`, `JUDGE_ADMIN_KEY`, optional `ALLOWED_ORIGINS`) are set with
`npx supabase secrets set --env-file <private file>` and are never committed.

## Known differences from the Docker version

* Python and JavaScript only (Java, C++ and C# need compilers that cannot run inside Supabase Free).
* Smaller hidden tests for 7 problems; memory limits 128 MB (Python) and 64 MB (JavaScript).
* Lobby "connected" status updates within about 10–35 s (heartbeats) instead of instantly.
* After the deadline, unfinished battle submissions get up to 180 s (was 100 s).
* Under a burst of simultaneous submissions, results queue for a free lane (measured: about 6–17 s with
  35 submissions at once).
